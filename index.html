프로젝트
그룹사 웹 서비스를 앱에 연동하는 범용 Hybrid WebView 프레임워크 (iOS)
개요
어떤 앱에도 진입점 하나로 붙는 하이브리드 WebView 프레임워크. WebView · JS 브릿지 라우팅 · 화면 이동 · MVI 화면 · 기본 브릿지를 프레임워크에 담고, 앱 고유 기능은 같은 계약으로 등록해 확장한다.
주요 성과
  1. WebView 메모리 사용량 약 70% 감소싱글톤 · 순환참조로 얽힌 Bridge 를 Navigator / API Bridge / SSO 세션 모듈로 분리해 순환참조와 Bridge Event 중첩 해소
  2. Bridge 인터페이스 통합 · 규격 문서화Bridge 마다 따로 있던 I/F 를 단일 I/F 와 규격 문서로 통합, WKScriptMessage → 브릿지 → Intent → UseCase 단방향 흐름으로 확장 기준 정립
  3. 그룹사 공통 SDK 플랫폼화RootView 진입점 하나와 계약 등록만으로 연동되게 설계, 그룹사마다 달랐던 WebView 구조를 공통 SDK 로 일원화
  4. Tuist 모듈화로 빌드 효율 개선Domain(UseCase) / Data(Repository) / Presentation 분리와 내부 · 외부 의존성 정리로 증분 빌드 적용, 필요한 모듈만 로드
  5. SwiftUI + MVI 로 금융 비즈니스 로직 분리단방향 데이터 흐름으로 화면 상태와 금융 로직 분리, Coordinator · DI(Swinject)로 Flow 단위를 나눠 연동 앱과의 결합도 최소화
  6. Swift Concurrency 기반 BridgeManagerBridge Event 를 Intent → UseCase 로 이어 처리하고 반복되던 Boilerplate 를 공통 모듈로 정리
  7. 인증 흐름 안정화OpenAPI · OAuth 인증 단계를 서비스별로 분리하고 ErrorCase 명세화, 세션 만료 시 화면 전환 오류 제거
  8. 테스트 가능한 구조 · 개발 가이드기능 · 서비스 단위 독립 테스트 구조 구축, Swift Testing 으로 브릿지 규격 적합성 테스트 351개 케이스 자동화, 개발 가이드 문서화

01모듈러 아키텍처

  • 프레임워크 모듈
  • 브릿지
  • 브릿지가 꽂히는 지점
  • 붙이는 지점은 하나앱은 RootView 하나로 웹 영역을 띄웁니다. 기존 화면 구조나 내비게이션을 바꿀 필요가 없습니다.
  • 확장은 계약으로기본 브릿지와 앱 고유 브릿지는 같은 프로토콜로 등록됩니다. 프레임워크는 앱의 업무 타입을 모릅니다.
  • 의존은 한 방향Navigator → Presentation → Domain ← Data. 화면 쪽은 BridgeManager → Model 로만 내려가고, Data 는 Domain 의 프로토콜을 구현합니다. 거꾸로 가는 import 는 없습니다.

02단방향 WebView Bridge + MVI + SwiftUI

  • 웹
  • 통로(WebView · 라우터)
  • 브릿지 + MVI 화면
  • 등록된 브릿지로 넘어가는 지점
  • 브릿지는 입력일 뿐브릿지는 UseCase 를 직접 부르지 않습니다. 부수효과는 Intent 에만 있고, 상태는 순수 Reducer 만 바꿉니다.
  • UI 는 상태로 띄운다확인 대화 상자도 Store 에 올리고 SwiftUI 가 그립니다. UIKit present 로 끼어들지 않습니다.
  • 대기는 수명으로 끝낸다타임아웃 대신 웹뷰 · 화면 · 대화 상자의 수명이 기다림을 끝냅니다. 답 없이 사라진 대화 상자는 오류로 응답합니다.

03한 번의 왕복 — 확인 대화 상자

웹이 showConfirm을 부르고 사용자가 "취소"를 누르기까지 코드가 지나는 순서입니다.

  1. 웹 라이브러리가 callbackID를 붙여 postMessage로 보낸다웹
  2. WebView 컨트롤러가 메시지를 봉투로 바꾸고, 처리 중 목록(inFlightTasks)에 올린다통로
  3. 라우터가 화면 이동 커맨드가 아니고 등록된 브릿지 커맨드임을 확인해 넘긴다통로
  4. 브릿지가 파라미터를 ShowConfirmParams로 디코딩하고 Intent 를 부른다브릿지 · MVI
  5. Intent 가 context.ask로 대화 상자를 Store 에 올리고, Reducer 가 줄에 세운다브릿지 · MVI
  6. State 가 바뀌어 SwiftUI .alert가 뜨고, 사용자가 "취소"를 누른다브릿지 · MVI
  7. View 가 Intent 에 답을 넘기고, Intent 가 답한 뒤 대화 상자를 내린다브릿지 · MVI
  8. 결과 {value:false}를 라우터가 응답 봉투로 감싼다통로
  9. JS 콜백이 같은 callbackID의 Promise 를 끝낸다웹

04설계에서 지킨 것

규격이 코드보다 먼저

iOS · Android · Web 이 같이 쓰는 브릿지 규격(JSON)을 서브모듈로 고정하고, 통로 이름 · 화면 이동 커맨드는 그 파일에서 코드로 생성합니다. 손으로 적은 값이 규격과 어긋날 자리를 없앴습니다.

규격 → 코드 생성 → 적합성 테스트 → PR 커밋 상태

적합성 검사를 머지 조건으로

규격의 모든 커맨드에 정상 · 필드 누락 · 타입 오류 · 허용값 밖 케이스를 돌려, 실패를 "동작 차이"와 "아직 구현 안 함"으로 나눕니다. 동작 차이가 있으면 머지가 막힙니다.

적합성 테스트 → PR 커밋 상태 → 머지 게이트

반복 작업은 템플릿으로

새 화면(State · Reducer · Intent · View · DI)과 새 브릿지 커맨드는 Tuist scaffold 로 만들고, 파일 배치 · 레이어 규칙은 검사 스크립트가 확인합니다.

tuist scaffold → 규칙 검사 스크립트
